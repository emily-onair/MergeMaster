Progress update · November 2026

MergeMaster

A merge queue for our team. Developers report a commit as ready to merge from inside Claude Code. Marc works through the requests in a web dashboard that checks each one against GitHub.

The project had two goals: to learn C# and .NET, and to build something the team actually uses.

1 · DeveloperRuns the report-merge skill on a feature branch
2 · APIChecks the commit against GitHub and stores the report
3 · MarcReviews, filters and syncs the queue in the dashboard

For developers: the report-merge skill

The skill is added to a repo under .claude/skills/. Running it reports the current branch and its latest commit as ready to merge.

Checks before anything is sent

  • It refuses to run on main.
  • It warns if the last commit was made by someone else.
  • It warns about uncommitted changes, which won't be part of the report.

What the developer provides

One answer: whether the request is urgent. Claude works out everything else, including tagging the change by reading the commits and changed files:

bugfixhotfixfeature extendsecuritychore docsclaudeother

Server-side checks on each report

The API rejects a report if:

  • a report already exists for that commit
  • the commit isn't on the reported branch
  • the commit has already been merged into main

For valid reports, it fetches the commit message from GitHub so the full message appears on the report.

For Marc: the dashboard

Working the queue

  • Open requests can be viewed as a table or as cards.
  • Filter by urgent only, author and tags. Search, sort by date, and page through results.
  • Archive finished requests, then restore or delete them from the archive.

Sync with GitHub

One button checks every open report against GitHub. It keeps stored names current and flags reports that have gone stale.

What it findsWhat happens
Repo or branch was renamedThe stored name is updated
Repo no longer existsThe report is flagged. Flags appear on the report, and a modal explains each one.
Branch no longer exists
Commit not found
Commit no longer on its branch
Commit already merged

Toast messages summarise what each sync changed. Reports that are already flagged are skipped to save GitHub API calls. If GitHub can't be reached, the sync stops cleanly and says so.

What I learned

  • ASP.NET Core: Razor Pages for the dashboard and an API controller for the skill, organised as MVC with reusable partial views
  • EF Core with SQLite: a schema across several tables (repos, branches, authors, tags, reports, sync flags), migrations, async queries
  • C# patterns: dependency injection, options binding for configuration, records and with expressions, extension methods
  • Talking to GitHub: a typed API client with a result/error pattern and a wrapper that handles network outages
  • Claude Code: writing a skill with a companion shell script

Current status

Everything above works locally. Before the team can use it:

  • Hosting. The skill currently posts to localhost.
  • Access control. The API and the dashboard have no authentication strategy.
  • Tests. Automated coverage is still light. Most testing so far has been manual.

Next steps:

  • Unit tests - I'm currently working through the Unit Tests module of my C# course and would like to thoroughly test the existing functionality before adding more features.
  • Notes - Marc can save notes about a specific report (possibly also the skill could ask the developer to add any notes additional to the commit message).
  • CMS style editing - the reports can be updated in the dashboard UI to address flags not automatically resolved.

Fortschrittsbericht · November 2026

MergeMaster

Eine Merge-Queue für unser Team. Entwickler melden einen Commit direkt aus Claude Code als bereit zum Mergen. Marc arbeitet die Anfragen in einem Web-Dashboard ab, das jede einzelne gegen GitHub prüft.

Das Projekt hatte zwei Ziele: C# und .NET zu lernen und etwas zu bauen, das das Team tatsächlich nutzt.

1 · EntwicklerFührt den report-merge-Skill auf einem Feature-Branch aus
2 · APIPrüft den Commit gegen GitHub und speichert die Meldung
3 · MarcPrüft, filtert und synchronisiert die Queue im Dashboard

Für Entwickler: der report-merge-Skill

Der Skill wird einem Repo unter .claude/skills/ hinzugefügt. Beim Ausführen meldet er den aktuellen Branch und dessen letzten Commit als bereit zum Mergen.

Prüfungen, bevor etwas gesendet wird

  • Er lässt sich nicht auf main ausführen.
  • Er warnt, wenn der letzte Commit von jemand anderem stammt.
  • Er warnt vor nicht committeten Änderungen, die nicht Teil der Meldung sein werden.

Was der Entwickler angibt

Eine einzige Antwort: ob die Anfrage dringend ist. Alles andere ermittelt Claude selbst, einschließlich der Tags für die Änderung, die es anhand der Commits und geänderten Dateien vergibt:

bugfixhotfixfeature extendsecuritychore docsclaudeother

Serverseitige Prüfungen jeder Meldung

Die API lehnt eine Meldung ab, wenn:

  • für diesen Commit bereits eine Meldung existiert
  • der Commit nicht auf dem gemeldeten Branch liegt
  • der Commit bereits in main gemergt wurde

Bei gültigen Meldungen ruft sie die Commit-Nachricht von GitHub ab, damit die vollständige Nachricht in der Meldung erscheint.

Für Marc: das Dashboard

Die Queue abarbeiten

  • Offene Anfragen lassen sich als Tabelle oder als Karten anzeigen.
  • Filtern nach „nur dringend“, Autor und Tags. Suchen, nach Datum sortieren und durch die Ergebnisse blättern.
  • Erledigte Anfragen archivieren und sie anschließend aus dem Archiv wiederherstellen oder löschen.

Synchronisierung mit GitHub

Ein einziger Button prüft jede offene Meldung gegen GitHub. Er hält gespeicherte Namen aktuell und markiert Meldungen, die veraltet sind.

Was gefunden wirdWas passiert
Repo oder Branch wurde umbenanntDer gespeicherte Name wird aktualisiert
Repo existiert nicht mehrDie Meldung wird markiert. Markierungen erscheinen an der Meldung, und ein Modal erklärt jede einzelne.
Branch existiert nicht mehr
Commit nicht gefunden
Commit nicht mehr auf seinem Branch
Commit bereits gemergt

Toast-Benachrichtigungen fassen zusammen, was jede Synchronisierung geändert hat. Bereits markierte Meldungen werden übersprungen, um GitHub-API-Aufrufe zu sparen. Ist GitHub nicht erreichbar, bricht die Synchronisierung sauber ab und weist darauf hin.

Was ich gelernt habe

  • ASP.NET Core: Razor Pages für das Dashboard und ein API-Controller für den Skill, aufgebaut nach MVC mit wiederverwendbaren Partial Views
  • EF Core mit SQLite: ein Schema über mehrere Tabellen (Repos, Branches, Autoren, Tags, Meldungen, Sync-Markierungen), Migrationen, asynchrone Abfragen
  • C#-Muster: Dependency Injection, Options-Binding für die Konfiguration, Records und with-Ausdrücke, Extension Methods
  • Kommunikation mit GitHub: ein typisierter API-Client mit Result/Error-Muster und ein Wrapper, der Netzwerkausfälle abfängt
  • Claude Code: einen Skill mit begleitendem Shell-Skript schreiben

Aktueller Stand

Alles oben Beschriebene funktioniert lokal. Bevor das Team es nutzen kann:

  • Hosting. Der Skill sendet derzeit an localhost.
  • Zugriffskontrolle. Für die API und das Dashboard gibt es noch kein Authentifizierungskonzept.
  • Tests. Die automatisierte Testabdeckung ist noch gering. Bisher wurde überwiegend manuell getestet.

Nächste Schritte:

  • Unit-Tests – Ich arbeite gerade das Modul zu Unit-Tests in meinem C#-Kurs durch und möchte die bestehende Funktionalität gründlich testen, bevor weitere Features hinzukommen.
  • Notizen – Marc kann Notizen zu einer bestimmten Meldung speichern (eventuell könnte auch der Skill den Entwickler bitten, zusätzlich zur Commit-Nachricht Notizen anzugeben).
  • Bearbeitung im CMS-Stil – Meldungen können in der Dashboard-Oberfläche bearbeitet werden, um Markierungen zu beheben, die nicht automatisch aufgelöst werden.
